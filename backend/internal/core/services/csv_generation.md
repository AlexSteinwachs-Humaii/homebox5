# Canonical CSV generation (worker contract)

`AllServices.CSVExports` is separate from ZIP export/import and attachments. API routes, download authorization, policies and expiry/deletion cleanup are delivered by subsequent stories. No list UI or separate local-save encoder is added here. Consumers must read the completed row's single server-selected artifact; never regenerate it to download/save. Incomplete/failed objects must not be served. Raw blob keys are sensitive and never client-selected.

## Encoding

`WriteCanonicalCSV` consumes the typed scalar projections from `CSVSources.Load`, never DOM data. Adapters return complete, authorized repeatable-read snapshots with no pagination cap. They currently materialize all rows in memory (O(rows × columns)); this is not a bounded-memory streaming adapter. The encoder writes sequentially to a mode-0600 temporary file; it does not construct a second full CSV string. The file is removed on all normal returns. Abrupt process termination can leave a local temporary file for OS temporary-directory housekeeping; no untracked remote object is created.

- UTF-8 without BOM, comma delimiter, double-quote escaping, LF record terminators, final LF. Unicode and embedded newlines are preserved. `encoding/csv` applies quoting; text is not trimmed or localized. Invalid UTF-8 and unsupported/non-finite scalars fail generation, not silently coerce.
- First row is the requested ordered machine column IDs; every row has exactly that width. No locale-dependent headings.
- Nil and empty strings encode as empty fields; booleans as `true`/`false`; UUIDs in canonical hyphenated form.
- Timestamps are UTC RFC3339Nano. Calendar dates are adapter-projected `YYYY-MM-DD`; absent dates are empty.
- Currency amounts are plain base-10 decimal amounts in the collection's currency units, without symbols/group separators or implicit cent conversion; quantities use the same non-exponent, shortest round-trip float64 representation. No forced two-decimal rounding. Integer counts/IDs use base-10 integers.
- Formula safety applies to **strings only**. For detection, skip any leading Unicode whitespace, control characters (including tab, CR, LF and NUL), or Unicode format characters (including BOM/zero-width space). If the next character is `=`, `+`, `-` or `@`, prefix an ASCII apostrophe to the **original** string. The original whitespace is preserved. Literal text `-12` is neutralized; the typed numeric value -12 is not. This is a documented spreadsheet import defense, not a guarantee against applications that remove apostrophes or later transform/reinterpret cell data.

## Queue, publication and retries

The database itself is the CSV queue. The API composition runs `Reconcile` immediately on startup and every ten seconds. It scans persisted queued jobs, running jobs with expired 15-minute leases, and due storage failures. No process-local pubsub delivery is required or authoritative; notification loss/restart cannot drop work. Serial processing bounds concurrent spool/upload work per process but not adapter snapshot memory. SQL errors leave intent for the next scan.

`Enqueue` validates current source access before allocating metadata and a fixed key `csv/{user}/{artifact}.csv`. Generation rechecks source access and capture consistency. `queued -> running` is a conditional update with an incremented attempt fencing token. Active duplicate deliveries do nothing. A generation/encoding failure records `generation-failed` (`source`/`encoding`); it requires explicit `Retry` by the original requester with current source authorization. Storage failures (`spool`, `upload`, `metadata`) record `storage-failed` and retry after one minute without a maximum attempt cap. Operators should monitor persistent failures. Retry never changes an already completed artifact.

After complete local encoding, publication begins a transaction and obtains a database write lock with an UPDATE guarded by running status and attempt token. The lock is held through upload and completion. An expired old generator cannot upload once a new attempt has claimed the row. A takeover cannot upload while another publication holds the lock. PostgreSQL locks the row; SQLite serializes **all database writers during upload**, an explicit throughput tradeoff for correctness with the existing immutable single-key schema. Very long uploads can therefore delay ordinary writes; errors/busy timeouts are recoverable. A future high-throughput variant needs persisted per-attempt blob keys and staged cleanup, not unfenced single-key uploads.

Completion happens only after successful upload/close. The same transaction reads current retention, fixes completion+expiry, records byte size and commits `completed`. Policy changes after completion cannot change this expiry. This is the primitive for the later retention story, not its public policy/cleanup APIs.

Partial/failed uploads and uploads followed by SQL failure retain their preallocated key and metadata; they are never considered completed or served. Retries overwrite that same key with a complete newly generated snapshot (data may have changed); only the successful attempt becomes canonical. No extra staging objects or lost-key orphan blobs exist. Cleanup must later remove blobs before deleting failed/pending metadata, including partial objects. A commit error can be ambiguous: the worker does not delete the blob or blindly revert state. A committed row remains completed (a conditional failure write cannot regress it); a rolled-back row becomes storage-failed if SQL is available, otherwise it remains running until lease reconciliation. Completed deliveries never overwrite the canonical bytes. SQL failure when recording an error also leaves a running lease that is recoverable. Client local-save errors never alter server state.

Selector/recent captures continue to require the trusted `CSVBoundaryAuthority` from the source-adapter contract, supplied with `WithCSVBoundaryAuthority`; without it these captures fail closed. This story does not invent a browser-supplied trust proof.
